# Orchestration slash commands

Global command files live in `~/.config/opencode/commands/`; the toolkit's copies are in `orchestration/commands/`. `install.sh` and `sync.sh` copy only the seven commands on the shared toolkit allowlist. Neither deletes commands or copies personal commands. Both back up replaced command files and refuse symlink paths. `sh sync.sh --commands-and-learning` limits sync to the toolkit commands and the two improvement skills. `/learn` does not run full sync: it mirrors only the exact approved changes.

| Command | What it does | Call behind it |
|---|---|---|
| `/note <text>` | Save the exact note in the active preset's ledger, with an agent tag if clear. | `agentgraph feedback --home H --text-file F [--agent NAME]` |
| `/learn [agent]` | Review all pending notes and recent chat excerpts, or just notes tagged with one agent. Propose up to eight lasting edits and apply only approved ones. | `agentgraph signals --home H --json --feedback-ids --no-cost` (add `--messages` only without an agent); `agentgraph improved --home H --keep-watermark --json-file F` for each applied edit; `agentgraph improved --home H --handled-file F` for settled items and any chat checkpoint |
| `/flows` | List drawn flows with their stored instructions. | `agentgraph structure flows --json` |
| `/flow A B [C…] [: instruction]` | Add one flow with an optional instruction. | `agentgraph structure flow add A B [C…] [--text-file F] --json` |
| `/agent-skills AGENT [add SKILL \| remove SKILL \| all]` | Show or change an agent's skills; changes apply on restart. | `agentgraph skills show AGENT`, `agentgraph skills add AGENT SKILL`, `agentgraph skills remove AGENT SKILL`, or `agentgraph skills all AGENT` |
| `/spend` | Summarize the cost trend in at most three lines. | `agentgraph cost --trend` |
| `/graph-check [task]` | Validate this project's graphs and report unfinished work. | `agentgraph check [--task NAME]` |

`H` is the active preset's ledger home; `F` is a temporary file. For `/learn`, `--feedback-ids` exposes the IDs used in the `{ "id": "reason" }` marking file. Marks are append-only in `H/feedback-handled.jsonl`; they do not rewrite notes, advance the watermark, or erase history. Recording an approved batch edit keeps the existing watermark, so notes not settled by that run remain pending.

Bloat: `agentgraph signals --json` carries `bloat` (`due`, the agents over budget or grown, each one's largest source); it is due only after `agentgraph bloat --set-baseline --home H`, and then `record` and `signals` print `improvement due: bloat`, which `/learn` and the improve skills answer with one shrinking edit. An applied edit's JSON may carry `size_change` (`{agent: characters}`); with a baseline, `improved` also records the measured change (`size_actual`). `agentgraph bloat` itself is read-only and never prints prompt text.

Hand edits: `agentgraph signals --json` also carries `hand_edits`, from files only (`edits.jsonl` in the home and the undo records in the backups folder, which default beside the home's `orchestration` folder; override with `--backups`, `--agents-dir`). `record` and `signals` print `improvement due: hand edits: AGENT's outputs were corrected by hand N times in D days across T tasks` when one agent's outputs were edited by hand (not undone) at least 3 times across at least 2 tasks in the last 14 days, and `AGENT's instruction was rewritten by hand N times in D days` for 3 or more rewrites of its instruction text; `--hand-days`, `--hand-edits`, `--hand-tasks` and `--hand-rewrites` change the window and thresholds. The agent with the most is named; an improvement recorded for that agent (its name in the file, summary, signals or size change) silences the edits before it. `/learn` and the improve skills answer it with one small edit to that agent's instruction. `python3 -m agentgraph.handedits` prints the measure per agent.

Cases: `agentgraph signals --json` also carries `cases` (`total`, `agents`: tune, held-out and replayable counts an agent, `edits`: the held-out and tune passes of each edit's trials) and prints `cases: AGENT N (T tune, H held-out, R replayable)`, from `cases.jsonl` and `replays.jsonl` in the home. `agentgraph cases` lists them (never a graph file's text), `cases --brief ID` prints the brief that replays one in a scratch worktree at its `base`, with the case's text inside a block labelled untrusted data, and `cases --result ID --outcome pass|fail --edit NAME` records a trial. The improve skills may read tune cases while drafting an edit; held-out cases are for trying the draft. Nothing starts an agent.

Verifier passes overturned: `agentgraph signals --json` also carries `verifier` (`passes`, `overturned`, `tasks`, `ways`: `sent_back`, `run_again`, `edited`, `feedback`; `days`, `thresholds`, `due`), and `record` and `signals` print `verifier: K of N passes overturned in D days`, or `improvement due: verifier: ...` at 2 or more in 2 or more tasks (the hand-edit window, `--hand-days`). A pass is a gate run by `verifier` that passed; it is overturned when, after it, a node it covered (its `feedback_to`, else its `depends_on`) was sent back by a later gate (another gate naming it evaluated as failed or refuted; read from the words of that gate's `evaluated` event note, never shown), run again (a `dispatched`, `retried`, `attempt` or `escalated` event), or had an output edited by hand and not undone (`edits.jsonl`), or when the user filed feedback naming `verifier` for that task (it overturns the task's latest pass before it). `record` stores the counts, the ids of the overturned gates and the passes in the run (`verifier`, only when the graph has a pass); `signals` adds the edits and feedback that came later. An improvement recorded for `verifier` silences the passes before it. The improve skills answer it with one small edit to the verifier's instruction.

Models changed: `agentgraph improved` and `agentgraph bloat --set-baseline` also store a fingerprint of the models in use: the preset's name and a hash of its agent-to-model map (each agent's model and variant). Nothing else of the preset file is stored, and nothing from it is ever printed. `agentgraph signals --json` carries `models` (`due`, `stored`, `now`: each only a preset name and a hash) and `record` and `signals` print one line, `improvement due: models: the models changed since the prompts were last reviewed (preset NAME)`, when today's fingerprint (the baseline's preset, read from the baseline's own config path) differs from the last stored one; the improve skills answer it with one deletion of a rule written for the old models. It is quiet when nothing was stored (no baseline was set, so `improved` stored none), when the preset cannot be read, or when nothing changed; the next recorded improvement, or a new baseline, clears it.

`--messages` reads the OpenCode V2 database in read-only mode. It returns up to 150 root-chat user messages, with at most 600 characters per excerpt and 30,000 characters of excerpt text total, plus a count of eligible messages omitted. It prefers original display text when available and excludes identifiable slash commands. A template saved as ordinary user text without presentation metadata cannot reliably be distinguished. A batch checkpoint advances separately from the single-proposal watermark; capped scans keep their backlog.

## Chat of one session

`agentgraph chat --session ID [--limit N] [--json | --text] [--chars N] [--demo]` prints one session's recent chat as capped plain text: the model's visible reasoning, messages, user prompts (a steered one included) and tool names with their status, never a tool's input or output. The latest 40 messages by default (at most 200); each text at most 2000 characters, the whole reply about 24000. It reads the OpenCode database read-only and never writes; a missing or locked database prints an empty feed with a warning. The web server serves the same feed at `GET /api/chat` (see `WEB_API.md`).

## Side chat

`agentgraph sidechat` is the back end of the view's "moon": a small read-only agent, `side-chat`, the user can ask about the running task. It talks only to the user, says nothing unless asked, has every tool denied (no file, shell, web or sub-agent), and has its own session. It never prompts, steers or interrupts any other session; the only session it is ever run in is the one it created, and an id from the main session's tree is refused.

- `agentgraph sidechat ask --main SESSION --text-file F|- [--json] [--full] [--dir PROJECT] [--demo]` asks one question (at most 4000 characters; one at a time, a second is refused while one is being answered). It returns the answer, the side session id, the model used, the route, the size of the brief and what the question cost. Each question carries a brief of at most about 24000 characters: the task graph (objectives; each node's id, status, agent, goal, evidence, capped), the list of the task's artifact files, the capped start of an artifact the question names (a node id or file name; only a plain text file under `.opencode/artifacts/<task>/`, never through a link), and the main chat as `agentgraph chat` prints it (no tool input or output). A later question in the same side session sends a section again only when it changed (`--full` sends all). It runs `opencode-cli run [--standalone] --agent side-chat --model M --format json` in the project folder with a timeout, by one of two routes chosen for each question: **service** (no `--standalone`: the shared background service answers; it holds the providers, so this is the route that works from the Desktop app, whose own process has none) when a service is running (`ps`, a fixed command with a short timeout) from the very CLI file about to be run, because a CLI of another version attached to that service would restart it; **standalone** (a private server that takes its providers from the caller's environment) in every other case. `AGENTGRAPH_SIDECHAT_ROUTE` = `service` | `standalone` | `auto` (the default) overrides the choice; `service` while the executables differ is refused with a one-line reason. The answer says which `route` it took and `status` shows the route the next question would take. A standalone failure about providers or credentials (`Model unavailable`, `api-key`, 401, 403) ends with what to do: open the side chat from an app whose background service is running. On the service route a timeout kills our `run` client and the service ends the turn with it (probed; `opencode-cli` has no command to stop a turn, so none is called), with the question and brief on its stdin (never in its arguments, so they are not in the process list); the model is `openai/gpt-6-luna`, and when that fails once the same question is asked with `anthropic/claude-haiku-5-5`. `OPENCODE_CLI` names another binary. The side session is created archived (out of the session list) and remembered per main session under `<project>/.opencode/sidechat/`.
- `agentgraph sidechat status [--main SESSION] [--json]` says whether the agent file is installed, the side session, its model, whether a question is being answered and what the side session has cost (read from the database).
- `agentgraph sidechat brief --main SESSION [--text-file F]` prints the sizes and section names of the brief the next question would send, never its text.
- `agentgraph sidechat install [--with-skill]` writes the agent file (and the skill, with the one rule that lets it load) from the shipped files `config/side-chat/{agent,skill}.md`; it refuses over an existing file and prints an undo record. `uninstall` removes only a file it wrote (its marker line is first) and keeps a backup; `undo RECORD` reverses either. Nothing runs `install` by itself.
- `--demo` (on ask, status, brief) answers from a fixed sample and calls nothing.

## Paths as commands

`agentgraph flow command ID --on` (or the graph view) makes a named path the command `/NAME`: it writes `NAME.md` into `~/.config/opencode/commands/` (`--commands DIR` for another folder). The file starts with the marker line `# agentgraph: flow command ...` in its frontmatter, sets only `description`, and its body is the path's run message (`agentgraph flow prompt`) with `$ARGUMENTS` as the goal, so `/NAME add a health endpoint` asks the orchestrator to run the path on that goal in the current session. Renaming the path renames the file, changing its instruction rewrites it, `--off` or removing the path deletes it, and undoing any of these writes the same bytes again. A file without the marker, or one whose bytes were changed by hand, is never replaced or removed. A file an earlier version of the toolkit wrote for the path (its template then: `agentgraph/flowearlier.py`) counts as the toolkit's: it is rewritten in the current shape, renamed with the path, and removed with `--off` or the path, as one this version wrote; turning the command `--on` again rewrites it. **What a command file cannot hold:** the run message from the graph view, the terminal panel or `flow prompt` names the other drawn paths that bind this run and the nodes to make check nodes (`GRAPH_FORMAT.md`); a command file is written once, and drawn paths change after it, so it holds no such list. Its body states the general rule (every other drawn path applies too, to each node of its first agent) and says to run `agentgraph flow prompt --name NAME --goal-file -` to see which apply now. Removing a path that can no longer be read (an agent on it is gone) deletes its command file too, under the same rule; `agentgraph structure flows` lists such paths under `unreadable`. The command's name is the path's name, so it follows `agentgraph/names.py` (`COMMAND_PATTERN`); a file name outside it is never read or written as a path's command.

Refused names: OpenCode's own commands (2.3.2: `init`, `review`, `goal`, the Desktop and terminal slash commands such as `reload`, `undo`, `new`, `compact`), the oh-my-opencode-slim plugin's (`deepwork`, `reflect`, `loop`, `interview`, `implement`), the seven toolkit commands above, and any existing file the toolkit did not write. An instruction holding `$ARGUMENTS`, `$1`…`$9` or a `` !` `` shell block is refused for a command, because OpenCode would replace or run it.

Measured on a scratch OpenCode 2.3.2 server with the plugin loaded (`.opencode/artifacts/agentgraph-desktop/n96/r1/command-proof.md`): a new command file is **not** live at once, despite the documentation quoted below; it appears after the configuration is reloaded (Desktop: `/reload`) or after a restart. The answer to `--on` says so (`applies`, `live: false`). On the same server, with a stand-in model that only recorded what it was sent (`n96/r2/at-reference-proof.md`): an `@path` file reference in a command's text is sent as plain text, never attached, inside a fenced block or not; so an instruction may hold one. **What a user types after `/NAME` is their own typing, and OpenCode treats it as it treats the text of any command: it runs a `` !`...` `` in it as a shell command, outside the agents' permissions, even inside the goal's fenced block. The toolkit never sees that text before OpenCode does and cannot check it; the command file it writes holds no such form.**

**Stale changes.** A path's `rev` (16 hex digits) is computed from its flow file's bytes; `flow command ID --on|--off`, `flow name`, `flow text`, `flow prompt` and `flow remove` take `--expect REV` and change nothing when the path changed since (`... changed since you opened it; reload and try again (rev now X)`, exit 1). An empty `--expect` is bad input, never taken as no `--expect`. A path removed and drawn again with identical bytes has the same `rev`: it is the same path, so a change expecting that `rev` is accepted.

## Path task graphs

`agentgraph flow scaffold P --task T` writes the task graph a path's run message describes (`GRAPH_FORMAT.md`, "Pool, escalation and groups from the structure folder"), so the orchestrator fills in goals and checks instead of laying out nodes. The run message ends by naming it; a command file's body names it too, and like the rest of that body it does not list which other paths or groups bind (the scaffold works that out when it runs). The command body before this line was added (`0859580`) is in `agentgraph/flowearlier.py`.

## Agents

`agentgraph agent add NAME` with no other option adds a blank agent (description "An agent you added. Open it to say what it does.", an empty instruction, the default verifier's model, writer permissions). `--template verifier` or `--copy-of AGENT` start from the verifier or a copy instead; `--model`, `--variant`, `--description`, `--prompt-file`, `--skills` and `--read-only/--no-read-only` replace a default. `agentgraph agent rename NAME TO` renames an added agent with its flows, groups and path commands in one undoable step; `agentgraph agent remove NAME` is refused while a path through the agent is a command (turn it off first). `agent text|rename|remove`, `skills add|remove|all`, `skill write|delete` and `team members|text|remove` take `--expect REV` as the path commands do. Every option of these commands is listed in `WEB_API.md`, "2. The commands".

## Presets and saved setups

`agentgraph preset show` prints the default preset (the top-level `preset` of `~/.config/opencode/oh-my-opencode-slim.json`), the preset names, and `Overridden by: env` when `OH_MY_OPENCODE_SLIM_PRESET` is set or `project` when a `.opencode/oh-my-opencode-slim.json[c]` in this folder or above sets one (by name only). `agentgraph preset switch NAME` changes only that one string, in place (every other byte stays), under the lock, after a dated backup, and prints a `record`. It applies at the next start of OpenCode; a session already open keeps its models. It refuses an unknown name, the preset already in use, and a switch an override would defeat. `agentgraph preset restore RECORD` puts the file back byte for byte, and is refused when the file changed since.

`agentgraph setup save NAME [--replace]` copies what the toolkit manages into `setups/NAME/` (git-ignored): the preset file, the native agent files that carry the toolkit's marker, the structure folder's agent files, `teams/` and `flows/`, the path command files that carry the marker, and `SKILLS.md`, with a manifest of SHA-256 and size. It never reads `opencode.json`, credentials, the prompts under `oh-my-opencode-slim/` or skill files. `setup list`, `setup show NAME` print names, counts, the date and the preset, never contents. `setup restore NAME` checks every hash first (a damaged setup is refused before anything is written), saves the current state of the same files as an undo record, then writes each file byte for byte and removes a managed file the setup does not have. `setup remove NAME` moves the setup into the backups folder. `setup undo RECORD` puts back everything a restore, remove or replace changed, byte for byte, and is refused when it changed since. `--json` prints the answer as JSON; `POST /api/setup` is the same through the page (`WEB_API.md`, section 3).

## Spend limit

`agentgraph spend limit AMOUNT [--warn AMOUNT]` keeps one limit in dollars for this project in `.opencode/spend.json` (next to the task graphs; `spend.lock` beside it), `agentgraph spend limit --off` takes it away, and `agentgraph spend show [--json]` prints the limit, what the tree has cost (chat against workers) and the rate. An amount is a plain number of dollars, above 0 and at most 1,000,000, with a leading `$` allowed and rounded to the cent. The warning amount defaults to 90% of the limit and must be below it. **Nothing is stopped at the limit.** The view draws the top total against it (`$7.65 / $50` with a thin line), in its attention colour from the warning amount, and says "at limit" or "over". The rate is the cost of the tree's last 30 minutes of messages, doubled, in dollars an hour (not shown when the database cannot give it). A spend file that cannot be read counts as no limit and is replaced by the next `limit`; its contents are never printed. The same is in the view's run details (the top total opens them) and `POST /api/spend` (`WEB_API.md`).

## OpenCode V2 command format

[OpenCode Commands](https://opencode.ai/docs/commands), read by the orchestrator on 2026-11-19 via `https://opencode.ai/v2/docs/commands`:

> Put global commands in `~/.config/opencode/commands/` and project commands in `.opencode/commands/`.
>
> Only `.md` files are discovered. Nested paths become command names with `/` separators.
>
> The trimmed Markdown body is always the prompt template.
>
> Do not put `template` in Markdown frontmatter.
>
> Use `$ARGUMENTS` for the complete argument string exactly as entered.
>
> Do not place untrusted arguments inside shell blocks.
>
> Later sources replace earlier commands with the same name.
>
> A custom definition can also replace an earlier built-in command.
>
> OpenCode reloads command files and configuration changes automatically.

The page calls `description` “Text shown in command lists and discovery” and says commands “run in the current session by default.” It documents `agent` for selecting another agent, `model` for selecting a model, `subagent: true` for a background child session (`false` forces the current session), and `subtask` as a deprecated alias. These files set only `description`, keep the current agent and session, and never use pre-submit shell blocks, which run “outside the agent's tool permission flow.”
