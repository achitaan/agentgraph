# Source-backed Markdown knowledge

Start by inspecting the existing organization. A new small collection can use
`sources/`, `notes/`, and `index.md`; these are conventions, not a schema migration.
Use Markdown links that work outside Obsidian. Preserve existing wikilinks and
frontmatter when working inside a vault. Treat `.obsidian` settings as user-owned.

## Ingest and synthesize

Retain source identity, title, author when known, URL or local path, publication
date, retrieval date, and access/privacy status. Keep a source copy only when its
retention is permitted and useful. Do not overwrite raw originals; add corrections
or a new version. A link and bibliographic record can be enough for restricted
or copyrighted material.

Derived notes should identify their sources and locations, separate reported
claims from inference, state uncertainty, and link to related concepts with a
reason for the relationship. Preserve contradictions instead of flattening them
into a false consensus. Repeated claims from derivative sources are not independent
corroboration. Record accepted decisions separately from proposals and experiments.

Update the index only for notes actually created or materially changed. Inspect
the target first and preserve human edits. Prefer a focused correction and a short
change note to rewriting the entire collection. Avoid copying sensitive work
material into a public personal repository.

## Query and maintain

Search the index and relevant notes, then inspect the underlying evidence needed
for the question. Cite sources, not just an earlier synthesis. Mark stale facts
and recheck volatile claims before treating them as current. Missing evidence is
an answerable limitation; don't fill it with invented knowledge.

For a requested maintenance pass, check broken links, source-less claims, duplicate
notes, conflicts, and stale decision status. Suggest or make only authorized
repairs; do not delete uncertain notes automatically. The graph of notes shows
relationships, not correctness, priority, or permission to act.

## Reuse successful work

When a repeated operation needs a durable record, extend the existing handoff or
run note with intent, prerequisites, exact commands, working directory, revision,
outcomes and the reason for the next decision. Link large outputs instead of
retaining transcripts; redact credentials. Reuse the existing note rather than
creating a parallel notebook system.

Before replaying a command, check its environment, inputs and present authority.
A recorded successful command can be stale or destructive on a second run. Keep
reusable procedures separate from one run's receipts. Promote only verified,
useful knowledge; a requested maintenance pass is enough without always-on ingest.
